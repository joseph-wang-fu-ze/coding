II. PRIVATEINFORMATIONRETRIEVAL
A. Problem Definition and Interface
Private Information Retrieval (PIR) is a protocol between a
client and one or more servers. It allows the client to retrieve
an entry from a public database hosted on the server(s),
without revealing to the server(s) which entry is retrieved.
The database DB consists of N entries. Theoretical explo-
rations of PIR often focus on the simplest case where each
entry is a single bit. In this article, we consider the more
general and practical setting with an arbitrary entry size of
w bits. In most of this article, we assume the N entries are
indexed by integers from 1 to N. Section VIII will deal with
a database whose entries are indexed by arbitrary keywords
instead of consecutive integers.
The database is public. Many clients, potentially anyone
with an Internet connection to the server(s), can interact with
the server(s) to retrieve their respective desired entries from
the same database. Each server stores a single copy of the
database (possibly preprocessed) regardless of the number of
clients it interacts with over time.
Theinteractionbetweentheclientandtheserverinasingle-
server PIR scheme is shown in Figure 1. The client has an
entry of interest that it wishes to retrieve. Let x denote the
indexoftheclient’sdesiredentry,alsocalledthedesiredindex
for short. Given the desired index x, the client constructs a
queryqandsendsqtotheserver.Fromtheclient’squeryqand
the database DB, the server computes a response r and sends
r to the client. Finally, using the server response r, the client
computes an answer, which should be equal to the desired
entry DB[x].
In a multi-server PIR scheme, the client’s query consists of
multiple components, one component per server. Each server
computes a response and sends it to the client. The client
computes the answer using all the responses.

B. Correctness and Privacy
APIRschememustsatisfycorrectnessandprivacy,defined
as follows:
• Correctness: The answer computed by the client in the
end equals the desired entry.
• Privacy: Informally, the server learns no information
about the client’s desired index from the client’s query.
In this article, we assume the server(s) are honest but
curious, i.e., the server(s) faithfully execute the steps of the
PIR scheme but may attempt to infer a client’s desired index
by analyzing the client’s query. In the single-server setting,
the server sees everything that an adversary in the network
sees. In the multi-server setting, it is further assumed that
the servers do not collude with one another. There is also
an implicit assumption that no adversary in the network can
see the client’s query to more than one server. Thus, in either
setting, we can treat the server(s) as the only adversary.
We also note that the PIR problem is not concerned with
theserver’sprivacy.Inparticular,theclientisallowedtolearn
information about the other entries in the database. This is
again because the entire database on the server is assumed to
be public. There are cryptographic primitives that do worry
about the server’s privacy. We will briefly contrast them with
PIR in Section II-D.

For computational PIR, it is more convenient to think of

In the case of multi-server schemes, each server plays the
game with the client and tries to guess b based on the client’s
query to it. The scheme satisfies privacy if the client wins the
indistinguishability game with each server.

ThemainefficiencymetricsforPIR(withoutpreprocessing)
are the communication and server computation costs.
• Communication:theamountofdata(typicallymeasured
in bits) exchanged between the client and the server(s).
Since there is a large gap between upload and download

communication cost into query size and response size.
• Server computation: the amount of computation per-
formed by the server(s) to compute the response.
Although the client also performs some computation to

VI. SERVER-PREPROCESSINGPIR
AllPIRschemes(withoutpreprocessing),includingthosein
the previous sections, have server computation costs that are
linear in the database size, since the server operates on every
single database entry. This is a fundamental barrier because,
intuitively, if a PIR scheme does not require the server to
operate on a given entry, then the server learns that the client
isnotretrievingthatentry,therebyviolatingPIRprivacy.This
intuition was formalized by Beimel, Ishai, and Malkin [57].
They proved the lower bound that Ω(N) server computation
is necessary if the server stores only the unmodified database
(and nothing else) and the client has no state.
The above linear server computation lower bound can be
circumvented by preprocessing the database. Note that any
nontrivial PIR scheme (with or without preprocessing) must
achieve sublinear communication (possibly in an amortized
sense). Naturally, many PIR schemes that use preprocessing
aim to make communication and server computation both
sublinear in N, so they have also been called doubly-efficient
PIR. But it is also important to note that not all PIR schemes
withpreprocessingaimtobedoublyefficient.Inparticular,the
scheme we present later in this section still has O(N) server
computation, but with an improved constant factor.
Iftheservercarriesoutthepreprocessingwithoutinvolving
any client, then it is called server-preprocessing PIR. If
preprocessingneedstobecarriedoutseparatelybyeachclient
or for each client, it is called client-preprocessing PIR. For
both paradigms, updates to the database pose new challenges,
since they likely require redoing a significant portion, if not
the entirety, of the preprocessing step. We discuss server-
preprocessing PIR in the rest of this section and client-
preprocessing PIR in the next section.
In a server-preprocessing PIR scheme, the server prepro-
cesses the original database in an offline phase and stores the
preprocesseddatabasetorespondtoclientqueriesinanonline
phase. The stored preprocessed database is inevitably larger
than the original database.
While there are a few doubly efficient server-preprocessing
PIRschemesintheliterature[57],[58],theyrelyonadvanced
tools and are beyond the scope of this article. Thus, in
this section, we describe a single-server server-preprocessing
PIR scheme whose online server computation is still O(N)
but a constant factor cheaper than the schemes mentioned
in Section V.
A. Background on LWE and RLWE Encryptions
As briefly mentioned in Section V, state-of-the-art single-

In LWE encryption, a plaintext m is a scalar, and a
ciphertext has the form m = (a,b), where a is a random
(cid:58)
vector and b is a scalar. Here, b=a·s+∆m+e, where the
vector s is the secret key, e is a small random error, and ∆ is
a scaling factor that places m in high-order bits. Decryption
works by computing b − a · s and rounding to the nearest
multiple of ∆ to remove the error e.
In RLWE encryption, a plaintext m is a polynomial, and
a ciphertext has the form m = (a,b) where a and b are
(cid:58)
both polynomials. Here, similarly to LWE, a is a random
polynomial and b=a·s+∆m+e, where s is the secret key
polynomial, e is a small random error polynomial, and ∆ is
the scaling factor. Decryption works similarly by computing
b−a·s and rounding to remove the error e.
The vector length in LWE and the polynomial degree in
RLWE are both denoted by n and typically range between
512 and 4096 for PIR. The bit-length of the scalar in LWE
and the polynomial coefficients in RLWE must be carefully
chosen based on n.
Computation efficiency comparison. Note that an LWE
ciphertext is more than n times larger than its plaintext,
whereas an RLWE ciphertext is only a constant factor larger
than its plaintext. This makes an RLWE-based SHE much
more efficient than an LWE-based one in terms of both com-

stems from the constant ratio between the ciphertext and
plaintext sizes. To understand the computational advantage of
RLWE, let us examine the computation involved in PtCtMul,

D. Adapting to the Single-server Setting
Manytwo-serverstatefulschemes,includingtheonewejust
presented, can be adapted to the single-server setting.
With only a single server, the client has to fetch hints from
the same server it sends queries to. Thus, the hints need to
be fetched from the server in a private manner, without the
server learning any information about them. This can be done
bystreamingtheentiredatabasetotheclientduringtheoffline
preprocessing phase. While streaming the database is costly
and inelegant, attemptsto fetch hints privatelywithout it [32],
[69], [70] have not yielded practical solutions.
In addition to the main hints, the client also needs to fetch
somebackuphintsinthepreprocessingphase[69].Thebackup
hints are used to replenish consumed hints after each query.
Eventually, the client will run out of backup hints. Thus, the
preprocessing phase needs to be executed periodically in the
single-server setting (rather than only once at the beginning
with two non-colluding servers).
It is worth noting that many existing single-server stateful
PIR schemes can achieve sublinear (in N) amortized commu-
nication from only one-way functions. (A recent work even
achieves this without any cryptographic assumptions [71].)
In contrast, single-server PIR with sublinear communication
without preprocessing is believed to require cryptographic
primitives stronger than one-way functions (Section II-D).

B. Cuckoo Hash Table
A cuckoo hash table uses several hash functions to insert
a set of N key-value pairs into an array CH whose size is
slightly larger than N. Typical parameter choices are two

|CH| ≈ 1.5N. The keyword PIR scheme in this section uses
the former. Let h and h denote two hash functions that map

element in CH starts with k.

IX. BATCHPIR
In the PIR variants discussed so far, we have assumed that
the client has a single entry to retrieve from the server. In
some applications, the client may want to retrieve a batch of
entries from the server. We call this variant batch PIR.
A. Problem Definition
InbatchPIR,theclienthasasetofbdesiredindicesorkey-
words {x ,x ,x ,...,x } and wants to retrieve all b entries

A trivial batch PIR scheme is to execute b instances of a
keyword/index PIR scheme in parallel. Doing so will require
b times the server computation cost of the underlying key-
word/index PIR scheme. Batch PIR schemes in the literature
aimtomakeservercomputationdependonlyonN andnoton
the batch size b. The communication cost inevitably depends
on b since the client needs to receive the b entries.
Note that preprocessing-based PIR schemes also assume
thattheclientwantstoretrievemanyentriesfromthedatabase.
So,preprocessing-basedPIRandbatchPIRaretwoparadigms
for improving the amortized server computation of PIR. The
difference between the two is that a batch PIR requires
the client to have the entire batch ready upfront, whereas
a preprocessing-based PIR allows the client to generate the
sequence of queries one by one, potentially dependent on the
answers to prior queries. In this sense, preprocessing-based
PIR is a stronger primitive and, as expected, is harder to
construct.

Batch PIR was first studied by Beimel et al. [57]. They

A. Live Caller ID Lookup
In 2024, Apple added a new feature, Live Caller ID, to
its phones [2]. A user’s phone will display the identity of
the incoming caller even if the caller is not in the user’s
contact list, or display “spam likely” if the caller has been
reportedbyotherusersassuch.Tosupportthisfeature,Apple
can maintain a database to map phone numbers to identities
(“suspected spam” can be a special identity). When a user
receives a call, the user’s phone could look up the database
usingtheincomingcaller’snumber.However,thiswouldallow
the server to learn who is calling the user, which is sensitive

[LEFT]
information that the user may not wish to disclose to Apple.
To enable the Live Caller ID feature without revealing the
caller’s number to Apple, the user’s phone sends a keyword
PIR query (the keyword is the caller’s number) to retrieve the
identity associated with the caller’s number [2].
B. URL Filtering
Another application of PIR deployed by Apple is URL
filtering[2].Inthiscase,abrowseroramobileapp(especially
one in parental control mode or designed for children) may
wanttoblockcertainwebsitesthatareknowntobeharmfulor
malicious.Similarly,Apple(oranothercompany)canmaintain
a database that maps URLs to website categories. But again,
the user may not want to reveal to the Apple server which
URL (legitimate or otherwise) it is visiting. PIR enables this
feature without revealing the user’s browsing history to the
server [2]. The browser/app can send a keyword PIR query
(the keyword is the URL) to retrieve what type of website
the URL corresponds to. The browser/app can then block a
harmful URL and display a reason.
C. Password Checkup
Billions of user passwords have been exposed as part of
data breaches that routinely make headlines. A user would
like to check if his passwords have been exposed and, if so,
choose new passwords. Some web services have compiled
databases of exposed passwords for users to query. But it
is a bad idea for a user to send their plaintext password to
query such a database – this is the very act of exposing their
password.KeywordPIRisanaturalsolutionhere(thekeyword
is the user’s password) by allowing a user to check whether
their password is in a database of exposed passwords without
revealing their password to the server [6], [7].
D. Anonymous Communication
Anonymous communication protocols allow users to ex-
change messages without others (such as Internet Service
Providers) finding out that they communicated. There are
severalproposalsforanonymouscommunicationsystems[3]–
[5]thatusePIR.WedescribeanaturalapproachusedinAngel
et al. [5].
Consider a system consisting of many users who wish to
talk to each other anonymously and an untrusted server to
facilitate.Theprotocolproceedsinrounds.Ineachround,each
user sends a key-value pair to the server, where the key is the
output of a PRF and the value is a message encrypted for
its intended recipient. Then, each user retrieves the encrypted
messageintendedforitusingasingle-serverkeywordPIR.For
this to work, the two users communicating need to agree on
the PRF secret key. Readers can refer to [5] for more details.
It is not hard to see that the server cannot link the sender and
recipient of a message due to PIR.
PIR has also been suggested [3] to improve the widely
used anonymous communication system Tor [94]. At a high
level, Tor consists of thousands of volunteer relays. Each
user randomly selects several relays to route their network

traffic. Each relay sees only the previous and next hops,
so the destination of the user’s traffic remains hidden. For
this to work, the user needs to retrieve the public keys and
IP addresses of the relays from a Tor directory authority.
However,iftheuseronlydownloadsinformationfortherelays

relays (such as their public keys and IP addresses) without
revealing which relays are selected.
XII. CONCLUSION
Private Information Retrieval (PIR) provides a principled
cryptographic approach for users to retrieve data from public
databases while keeping their queries hidden from service
providers and network observers. In this article, we surveyed
the main design paradigms for PIR by organizing the design
space along three key aspects: the number of servers, the
securityassumptions,andtheuseofpreprocessing.Wepresent
conceptuallysimpleconstructionstoconveythecoreideasand
essential techniques underlying each paradigm. We provided
anoverviewoftheperformancecharacteristicsofdifferentPIR
paradigms and their trade-offs. We also described common
applications of PIR and discussed important extensions of
PIR, including keyword PIR and batch PIR, which are crucial
for practical deployments where data is usually indexed by
arbitrary strings and multiple queries naturally occur.
PIR remains an active area of research. Further improving
performance (both asymptotically and concretely), relaxing
assumptions, supporting dynamic databases, developing better
implementations, and deploying real applications all continue
to be interesting and important research directions. We hope
this article equips readers with a clear conceptual map of
the PIR landscape and serves as a starting point for further
exploration of both the theoretical foundations and practical
systems of Private Information Retrieval.
